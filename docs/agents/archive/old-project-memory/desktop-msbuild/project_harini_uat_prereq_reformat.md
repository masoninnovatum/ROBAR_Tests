Customer request (2026-09-28, relayed by Mason): rewrite each UAT's prerequisites "in the format the formal scripts detail them," and check for GlobalSettings mentioned in a step but missing from prerequisites. Piloted on `UAT_MDM_MasterDataManagement.doc` before rolling out further (only MDM and the Attachments/Link Management doc below are done as of this writing — the other 18 UATs still need this pass).

**Format discovered from formal scripts** (confirmed via `MDM_Actions5.1.doc` and `MDM_Workflow_Lock19.1.doc`'s Setup Requirements tables): GlobalSettings are phrased as *"Within the GlobalSettings table, if the SettingName "X" exists with a SettingOwner = "Y", ensure that the Value is set to "Z"."* Adapted (per user iteration) to a more compact form once the type-grouping/bold convention was established: `**SettingName** - GlobalSetting (SettingOwner = "X"); <value clause>.`

**Final prerequisites convention (after 4 rounds of user feedback), in this order:**
1. `Environmental Settings:` heading first — this now holds BOTH GlobalSettings/PrintConfigs (script-style phrasing, bold setting name) AND catch-all facts with no single named test-data element. Do NOT create a separate `Settings:` heading elsewhere in the doc — everything environmental/settings-related goes here at the top, in one place. (This merged an earlier iteration that had a separate `Settings:` heading at the bottom — that was wrong; fixed on MDM and Attachments_LinkManagement 2026-09-28, apply the merged version from the start on the remaining 18.)
2. `Users:` — every User alias grouped consecutively.
3. `Items:` (or a domain-appropriate type name, e.g. `Attachments:` for attachment aliases) — every same-type element grouped consecutively, not interleaved by feature section.
4. `Schemas:`, `Label Types:`, `Files:` etc. as needed per UAT's actual data types.
- No more `a) b) c)` lettering anywhere.
- Every named test-data element is its own line: `**ElementName** - description`, with only the element name bold (verified character-by-character via Word COM after each build — `Font.Bold` must cover exactly the name, not the dash or description).
- Facts with no clean single alias stay as plain (non-bold) sentences within whichever heading fits, or under Environmental Settings if none fits.

**Build script change:** `build_consolidated.ps1` (in `_uat_build_sources\`) now has a `Write-PrereqCell` function that parses `**bold**rest` markers per prerequisite line and applies real mixed bold/non-bold formatting via Word COM Range manipulation (previously the whole cell was force-unbolded). This function is now load-bearing for every future rebuild — do not revert to the old `$preqCell.Range.Text = (...) -join "`r"` one-liner.

**Global-settings audit finding:** `AttachEditIncrementSeqNum` was referenced in a step's expected result but never listed in prerequisites — in BOTH the old combined doc and even our own already-delivered, more mature `attach_consolidated.json` content (AM_AttachmentManagementAndUpload / LM_LinkManagement). This is likely the exact instance the customer flagged. Its SettingOwner (confirmed from formal script `AM_Edit.doc`) is `Innovatum.Pages.LinkAttachmentManagement.WCF`, default `N`. **Not yet fixed in `attach_consolidated.json` itself** (those two UATs aren't currently delivered — see below) — worth fixing there too if they're ever rebuilt, and worth specifically checking for on every remaining UAT during the reformat pass, not just relying on memory of settings already known.

**User security-description convention (added 2026-09-28, confirmed against formal scripts `AM_BasicFunctions`, `AM_Edit`, `AU_BasicFunctions`):** formal scripts describe a test user's security either as "A user associated with the AllSecurity group" (unrestricted) or "A user with all security processes enabled except for X" (restricted — X is only what that user is specifically being tested for lacking). They never enumerate a whitelist of just-the-needed-processes the way our docs previously did. Applied convention: **User** - an all security user.` when the user is never tested for lacking any permission (even if they're specifically the one exercising an interesting permission like Override_Lock — exercising a capability positively is not the same as being tested for lacking one); `**User** - a user with all security processes enabled except for X, Y.` when the UAT does test that the user lacks specific named process(es). Before rewriting a user's line, check whether any step tests that user being blocked/disabled from something — if yes, list exactly what's missing (matching the step); if no, it's an all-security user regardless of which specific processes happen to be relevant to what they do. Applied to `UAT_Attachments_LinkManagement.doc`'s User 1 and User 2 (both all-security, since neither is tested for lacking anything). Apply this check to every user across the remaining 18 UATs during the reformat pass.

**Results/Conclusion section convention (added 2026-09-28):** the Conclusion table cell should be one paragraph per feature/topic (split on the natural sentence-per-topic boundaries the conclusion was already written with), not one dense block paragraph. Just insert `\r` between topic sentences in the JSON `conclusion` string — `build_consolidated.ps1` writes it via a plain `Range.Text =` assignment, and `\r` already renders as a paragraph break there (no build-script change needed, unlike the prerequisites bold formatting). Applied to MDM and Attachments_LinkManagement 2026-09-28. Apply to the remaining 18 during their reformat pass.

**Test-data bolding extended into step text (2026-09-28):** `build_consolidated.ps1` now also bolds every occurrence of a known alias name (Users, Items, Templates, LCNs, Settings, etc. — anything that was bolded in the Prerequisites table) wherever it appears within a step's instruction or expected-result text, not just in the Prerequisites table. Implementation: `Get-AliasNames` extracts every `**name**` from the UAT's prerequisites array; `Get-BoldSpans` finds all non-overlapping whole-word matches of those names in a block of text (regex with `(?<![A-Za-z0-9_])`/`(?![A-Za-z0-9_])` boundaries, so e.g. `ITM1` never matches inside `ITM10` or `ITM-G1`); `Write-RichCell` writes the text into a Word cell in bold/non-bold segments accordingly. Applied to the steps table (Table 6, column 2) for all 19 UATs — purpose/prerequisites/conclusion are unchanged by this (prerequisites already had their own bolding from the earlier reformat). Verified via Word COM character-by-character checks on two docs (SM: "User 3" bolds cleanly with nothing else; MDM: "ITM-G1" bolds as one unit, doesn't get confused with "ITM1"). All 19 rebuilds' step counts still matched exactly. This is now a permanent feature of `build_consolidated.ps1` — any future rebuild will automatically bold alias mentions in steps, driven purely by whatever is bolded in that UAT's prerequisites array.
